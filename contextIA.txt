## DESCRIPCIÓN DEL SERVICIO

Microservicio responsable de gestionar el historial clínico electrónico
de las mascotas dentro de la plataforma PetWell. Es un servicio
completamente independiente: NO almacena datos en el Pet Service.

Forma parte del ecosistema PetWell:
  - API Gateway      → puerto 3001 (entrada centralizada)
  - Pet Service      → puerto 3002 (mascotas y dueños)
  - User Service     → puerto 3003 (usuarios y clínicas)
  - EHR Service      → puerto 3004 (este servicio)

## ROLES Y PERMISOS
================================================================

- DUENO_MASCOTA:
  * Puede consultar el historial clínico (EHR) y vacunas de SUS mascotas limitadas por relacionalidad (pet_owners en Pet Service / validación JWT).
  * Puede descargar el PDF resumido del historial.
  * No puede realizar cambios médicos (ej. asentar un diagóstico o registrar vacuna).

- VETERINARIO:
  * Puede leer todo el historial siempre que interactúe bajo una clínica.
  * Único rol habilitado desde Agenda Front-End para "Registrar Vacuna".
  * Puede descargar PDF para adjuntar o compartir.

- CLINIC_ADMIN:
  * Posee accesos generales de lectura médica.
  * Bloqueado por interfaz para prevenir registros médicos erróneos (No ve botones de "Registrar Vacuna").

## ENDPOINTS
================================================================

Base URL: /api/v1

GET  /health
  → Health check del servicio
  → Respuesta: { status: "ok", service: "ehr-service" }

--- EHR Records ---

POST /ehr
  → Crear nuevo registro médico
  → Requiere: role === CLINIC_ADMIN || VETERINARIO
  → Valida que la mascota pertenezca a la clínica del usuario
  → Body: { pet_id, visit_date, veterinarian_id?, reason?,
            anamnesis?, diagnosis?, treatment?,
            prescriptions?, lab_results?, notes? }
  → clinic_id: se extrae del JWT (NUNCA del body)
  → Respuesta 201: EhrRecordPublic

GET  /ehr/pet/:petId
  → Obtener historial completo de una mascota
  → OWNER: ve todos los registros (valida ownership via Pet Service)
  → CLINIC: ve todos los registros si tiene permiso en ehr_permissions,
             si no, solo ve sus propios registros
  → Respuesta 200: EhrRecordPublic[]

GET  /ehr/:id
  → Detalle de una consulta específica
  → OWNER: valida que la mascota le pertenece
  → CLINIC: valida que record.clinic_id === user.clinic_id
             OR existe permiso en ehr_permissions
  → Respuesta 200: EhrRecordPublic

PUT  /ehr/:id
  → Actualizar un registro médico
  → Requiere: role === CLINIC_ADMIN || VETERINARIO && record.clinic_id === user.clinic_id
  → Body: campos opcionales (todos excepto pet_id y clinic_id)
  → Respuesta 200: EhrRecordPublic

DELETE /ehr/:id
  → Eliminar un registro médico
  → Requiere: role === CLINIC_ADMIN || VETERINARIO && record.clinic_id === user.clinic_id
  → Respuesta 200: { data: null }

--- Consentimiento (v2) ---

POST /ehr/permissions
  → OWNER otorga acceso a una clínica
  → Requiere: role === OWNER
  → Body: { pet_id, clinic_id }
  → Valida: pet existe, caller es dueño, clinic_id es UUID válido
  → Respuesta 201: EhrPermissionRow

DELETE /ehr/permissions
  → OWNER revoca acceso a una clínica
  → Requiere: role === OWNER
  → Body: { pet_id, clinic_id }
  → Error 404 si el permiso no existe (DELETE protection)
  → Respuesta 200: { data: null }

GET  /ehr/permissions/:petId
  → Lista clínicas autorizadas para una mascota
  → OWNER: debe ser dueño de la mascota
  → CLINIC: debe tener permiso en ehr_permissions
  → Respuesta 200: EhrPermissionRow[]

--- Auditoría (v3) ---

GET  /ehr/audit/:petId
  → Historial de acciones sobre registros de una mascota
  → OWNER: debe ser dueño
  → CLINIC: debe tener permiso en ehr_permissions
  → Respuesta 200: EhrAuditLogRow[]

--- Vacunas (v5) ---

POST /ehr/vaccinations
  → Registrar una vacuna aplicada a una mascota
  → Requiere: role === CLINIC_ADMIN || VETERINARIO
  → clinic_id: siempre del JWT (nunca del body)
  → Si role === VETERINARIO y veterinarian_id no se pasa, se usa user.sub
  → Guarda duplicados: rechaza si la misma vacuna fue aplicada ±30 días antes
  → Body: { pet_id, vaccine_name, application_date, next_due_date?,
            batch_number?, veterinarian_id?, notes? }
  → Emite evento: vaccination.created (console.log estructurado)
  → Respuesta 201: VaccinationPublic
  → Error 409: Duplicado detectado (±30 días)

GET  /ehr/:petId/vaccinations
  → Lista todas las vacunas de una mascota, más recientes primero
  → OWNER: verifica ownership vía Pet Service
  → CLINIC: su clinic_id o permiso en ehr_permissions
  → Respuesta 200: VaccinationPublic[]

--- Exportación PDF (v5) ---

GET  /ehr/:petId/export/pdf
  → Genera y descarga historial clínico completo en PDF
  → Acceso: mismo control que EHR getRecordsByPet
  → Contenido:
      Sección 1: Encabezado (PetWell, fecha generación)
      Sección 2: Datos de la mascota (nombre, especie, raza, edad, peso)
      Sección 3: Historial clínico (ehr_records en orden cronológico)
      Sección 4: Tabla de vacunas (vaccine_name, fecha, próxima dosis, lote)
  → Librería: PDFKit (pure Node.js, sin Chromium)
  → Content-Type: application/pdf
  → Content-Disposition: attachment; filename="historial-{petId}.pdf"
  → Respuesta 200: Buffer PDF

## MODELO DE SEGURIDAD
================================================================

Autenticación:
  Todas las rutas requieren Authorization: Bearer <JWT>
  JWT generado por User Service (clave compartida JWT_SECRET)

Payload JWT esperado:
  { sub, email, role, clinic_id?, iat, exp }

Control de acceso por operación:

  Operación            | DUENO_MASCOTA                | CLINIC_ADMIN                              | VETERINARIO
  ---------------------|------------------------------|-------------------------------------------|-------------------------------------------
  Ver historial        | ✅ (mascotas propias)          | ✅ (su clinic_id o permiso ehr_permissions) | ✅ (su clinic_id o permiso ehr_permissions)
  Ver registro único   | ✅ (mascotas propias)          | ✅ (su clinic_id o permiso ehr_permissions) | ✅ (su clinic_id o permiso ehr_permissions)
  Crear registro       | ❌                            | ✅ (clinic_id del JWT + validación mascota) | ✅ (clinic_id del JWT + validación mascota)
  Editar registro      | ❌                            | ✅ (solo los de su clínica)                 | ✅ (solo los de su clínica)
  Eliminar registro    | ❌                            | ✅ (solo los de su clínica)                 | ✅ (solo los de su clínica)
  Otorgar permiso      | ✅ (mascotas propias)          | ❌                                         | ❌
  Revocar permiso      | ✅ (mascotas propias)          | ❌                                         | ❌
  Ver permisos         | ✅ (mascotas propias)          | ✅ (si tiene permiso)                      | ✅ (si tiene permiso)
  Ver auditoría        | ✅ (mascotas propias)          | ✅ (si tiene permiso)                      | ✅ (si tiene permiso)

Flujo de consentimiento cruzado:
  1. OWNER llama POST /ehr/permissions con { pet_id, clinic_id }
  2. EHR Service verifica: caller es dueño (via Pet Service)
  3. Se inserta fila en ehr_permissions
  4. La clínica ahora puede ver TODOS los registros de esa mascota
  5. OWNER puede revocar con DELETE /ehr/permissions

Principios de seguridad:
  - clinic_id jamás se acepta del body del request
  - Una clínica NO puede auto-asignarse permisos (solo OWNER)
  - clinic_id en permisos debe ser UUID válido (formato validado)
  - DELETE de permiso inexistente retorna 404 (no silent no-op)
  - El dueño puede consultar todo el historial de su mascota
  - Auditoría es fire-and-forget: nunca bloquea operaciones de negocio

## COMUNICACIÓN ENTRE SERVICIOS
================================================================

→ Pet Service (puerto 3002):
  Endpoint: GET /api/v1/pets/:petId
  Propósito:
    1. Verificar que el dueño (OWNER) tiene acceso a la mascota
    2. Verificar que la mascota existe antes de otorgar permisos (404 si no)
  Header: Authorization: <token>   ← incluye el prefijo "Bearer "
  Respuesta esperada: { data: { owner_ids: string[] } }

  Si el Pet Service devuelve 404 → se lanza error 404 (mascota no existe).
  Si el Pet Service no responde → se deniega el acceso (fail-secure).

## SEGURIDAD — ROW LEVEL SECURITY (RLS)
================================================================

Script: database/rls_security.sql
Ejecutar DESPUÉS de schema.sql y migration_v2_permissions_audit.sql

Estado RLS por tabla:

  Tabla              | RLS  | Políticas
  -------------------|------|----------
  ehr_records        | ✅   | SELECT: staff misma clínica, cross-clínica con permiso, DUENO read-only
                     |      | INSERT/UPDATE/DELETE: CLINIC_ADMIN + VETERINARIO misma clínica
  ehr_permissions    | ✅   | SELECT: owner (propias), staff (su clínica)
                     |      | INSERT: solo DUENO_MASCOTA como granted_by (anti-auto-grant)
                     |      | DELETE: solo DUENO_MASCOTA (revocación)
                     |      | Sin UPDATE — revocar = eliminar y volver a crear
  ehr_audit_logs     | ✅   | SELECT: owner (por actor_id), staff (por clinic_id)
                     |      | INSERT: permitido (service role lo usa)
                     |      | Sin UPDATE ni DELETE — INMUTABLES por diseño
  vaccinations       | ❌   | Sin RLS — acceso controlado 100% en service layer

Helper function:
  public.jwt_claim(claim TEXT) → extrae claim del JWT con NULLIF seguro
  Accede a: current_setting('request.jwt.claims', true)::json ->> claim
  Se creó en PUBLIC (no en auth.*) para evitar el error de permisos.

Claims JWT usados:
  sub       → UUID del usuario
  role      → DUENO_MASCOTA | CLINIC_ADMIN | VETERINARIO
  clinic_id → UUID de la clínica (null para DUENO_MASCOTA)

Protecciones adicionales implementadas:
  - ehr_permissions solo puede ser insertada por DUENO_MASCOTA
    (clínicas NO pueden auto-asignarse permisos)
  - ehr_audit_logs no tienen UPDATE ni DELETE policy
    (inmutabilidad total del registro de auditoría)
  - clinic_id en ehr_records siempre debe coincidir con el JWT
    (aislamiento criptográfico entre clínicas)

Nota importante sobre Service Role:
  La capa Node.js usa SUPABASE_SERVICE_ROLE_KEY que bypassa RLS.
  Estas políticas protegen acceso directo a la BD.
  Validación de negocio (ownership, permissions) en service layer.
